Memoria técnica de la solución implementada.

1. Introducción y objetivos

El objetivo de esta práctica es construir un videoclub distribuido mediante dos microservicios independientes. Los usuarios pueden registrarse, autenticarse, consultar un catálogo de películas, recargar su saldo, reservar películas en un carrito, pagar el carrito y valorar películas. Los administradores pueden gestionar el catálogo y consultar el historial de ventas por año y país.

La solución utiliza PostgreSQL como fuente única de datos, Docker Compose para orquestar los contenedores, Quart como servidor HTTP asíncrono y SQLAlchemy Core con el dialecto asíncrono de PostgreSQL para todas las consultas desde Python.

2. Planificación del desarrollo

Se ha seguido la planificación recomendada en el enunciado. Esta división permite cerrar primero la consistencia de los datos, después exponerla de forma segura mediante los servicios y, finalmente, medir y documentar el rendimiento.

Los dos servicios se encuentran en la red privada de Compose y acceden al host database. Desde el ordenador se publican los puertos indicados para poder ejecutar el cliente y observar las respuestas.

3.2. Persistencia y configuración

PostgreSQL utiliza el volumen p2_database_data, montado en /var/lib/postgresql/data. Los scripts database/schema.sql y database/populate.sql se montan en /docker-entrypoint-initdb.d y se ejecutan automáticamente la primera vez que se inicializa un volumen vacío.

El secreto de sesión se proporciona mediante .env y no se incluye en el repositorio. .env.example sirve como plantilla y los dos servicios reciben el mismo valor de TOKEN_SECRET.

5. Triggers y funciones almacenadas

5.1. Gestión automática del carrito

  • manage_cart_film_stock(): bloquea el carrito, comprueba que está abierto y descuenta stock al insertar o aumentar una línea. Al borrar o reducir unidades, devuelve el stock.
  • recalculate_cart_total(): recalcula carts.total_price después de cada cambio en cart_films.
  • handle_cart_status_change(): al cambiar a paid, comprueba saldo, descuenta el coste y establece paid_at. Impide pagar carritos vacíos o pagar dos veces.

6. Implementación de los microservicios

6.1. SQLAlchemy Core asíncrono

La conexión se configura con create_async_engine y AsyncSession. Todas las rutas que acceden a PostgreSQL son async def y ejecutan las sentencias con await session.execute(text(...), parametros). 

async with async_session() as session:
    async with session.begin():
        result = await session.execute(
            text("SELECT ... WHERE film_id = :film_id"),
            {"film_id": film_id},
        )

Las consultas son parametrizadas. No se interpolan datos recibidos por HTTP en el SQL. Las operaciones complejas combinan autenticación y modificación de datos con CTEs o funciones SQL para respetar el requisito de un único execute() por operación.

6.2. Autenticación stateless

Al iniciar sesión se incrementa session_version. El token contiene internamente el identificador y la versión, y se cifra con Fernet usando una clave derivada de TOKEN_SECRET. El token se envía en Authorization: Bearer <token>. No se almacenan tokens. Cada endpoint protegido descifra el token y valida en SQL que el usuario sigue activo y que la versión coincide. Login, logout y baja lógica invalidan tokens anteriores.

8. Optimización de ventas

8.1. Problema inicial

El informe une carts, users, cart_films y films, filtra por compras pagadas, año de pago y país, y ordena por fecha, carrito y película. La versión inicial aplicaba EXTRACT(YEAR FROM paid_at). Al aplicar una función sobre la columna, un índice normal sobre paid_at no puede utilizarse de forma eficaz para localizar directamente el intervalo.

8.2. Estrategia

  1. Ejecutar el plan base con EXPLAIN (ANALYZE, BUFFERS, VERBOSE).
  2. Crear el índice parcial carts(paid_at, user_id, cart_id) WHERE status = 'paid'. Solo almacena las filas que puede devolver el informe.
  3. Crear el índice funcional users(LOWER(country), user_id), coherente con el filtro insensible a mayúsculas.
  4. Sustituir el filtro del año por paid_at >= inicio y paid_at < fin. Este predicado permite un index scan o bitmap index scan según el tamaño de la tabla y la distribución.
  5. Repetir el mismo EXPLAIN y comparar coste estimado, tiempo real, buffers leídos y nodos de acceso.

Todas las sentencias están en database/optimizacion.sql. El script también reemplaza sales_by_year_country() para que la API aplique la misma estrategia, no solo el ejemplo de laboratorio. 

psql "postgresql://alumnodb:1234@localhost:9999/si1" \
  -f database/optimizacion.sql
Los tiempos y el plan exacto dependen de la cantidad de filas, estadísticas y caché del servidor. La comparación que se entregue debe acompañarse de las salidas obtenidas en el entorno de ejecución. En una base pequeña es normal que PostgreSQL elija un sequential scan porque resulta más barato; el índice sigue siendo útil cuando crece el histórico.

9. Seguridad, consistencia y decisiones

  • Las contraseñas no se almacenan en claro; se guarda su hash SHA-256.
  • Los tokens son Fernet y el secreto se configura fuera del repositorio.
  • Los valores HTTP se envían como parámetros de SQLAlchemy, evitando inyección SQL.
  • Los pagos se realizan dentro de una transacción y el descuento verifica saldo suficiente.
  • Los triggers serializan el acceso al carrito y actualizan stock y total en la base de datos, evitando inconsistencias entre clientes.
  • Las películas y usuarios se desactivan lógicamente para conservar el historial de operaciones.
  • Las restricciones de PostgreSQL actúan como última barrera de integridad, incluso si otro cliente accede directamente a la base de datos.

10. Organización de la entrega

La entrega debe ser un único archivo P2.zip con los fuentes, scripts SQL, dependencias, Docker Compose, cliente y esta memoria en PDF. No deben incluirse entornos virtuales, cachés, bytecode ni metadatos del sistema operativo. 

find . -type d \( -name __pycache__ -o -name .venv -o -name venv \) \
  -prune -exec rm -rf {} +
find . -type f \( -name '*.pyc' -o -name '*.pyo' \) -delete
zip -r P2.zip . -x '*.git/*' '*.env' '*.venv/*' '*__pycache__/*'

Antes de comprimir se debe levantar la aplicación desde un volumen limpio, ejecutar el cliente, guardar capturas de las pruebas, ejecutar la optimización y añadir las salidas de EXPLAIN a la memoria.

11. Conclusiones

La implementación separa claramente la gestión de usuarios de la lógica del videoclub, manteniendo una única base de datos transaccional. La lógica crítica de stock, totales y pagos reside en PostgreSQL mediante triggers y funciones, mientras que Quart expone una interfaz REST asíncrona y parametrizada. El cliente automatiza tanto los casos normales como los errores y el script de optimización deja reproducible la comparación del informe de ventas.
